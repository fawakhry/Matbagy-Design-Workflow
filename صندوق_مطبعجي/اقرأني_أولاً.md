# 0) غرفة مطبعجي المشتركة — User + ChatGPT + Gemini

تم اعتماد معماريًا فكرة غرفة داخل منصة مطبعجي يكون المستخدم طرفًا ثالثًا كاملًا فيها مع ChatGPT وGemini.

**الحالة الحالية:**

`APPROVED_ARCHITECTURE / NOT_YET_IMPLEMENTED_IN_PRODUCTION`

وجود القواعد هنا لا يعني أن APIs أو الواجهة تم نشرها أو اختبارها إنتاجيًا بعد.

## المبدأ

منصة مطبعجي هي الـ`AI Orchestrator` والوسيط الوحيد:

`User <-> Matbagy Orchestrator <-> ChatGPT`

`User <-> Matbagy Orchestrator <-> Gemini`

لا يعتمد النظام على أن ChatGPT وGemini يتصلان ببعض مباشرة. المنصة تمرر الرسائل والسياق وتمنع الحلقات اللانهائية.

## الأدوار

### ChatGPT

`Design Orchestrator + Memory Manager + Workflow Planner + Final Synthesizer`

مسؤول عن فهم الطلب، استرجاع ذاكرة صندوق مطبعجي، إدارة Case/Order/Asset IDs، تحديد متى نحتاج Gemini، دمج النتيجة، وإرجاع قرار موحد للمستخدم.

### Gemini

`Visual Intelligence + Design Reviewer + Reference Comparator`

مسؤول عن تحليل الصور والمراجع، مقارنة النسخ، Visual QA، فحص layout/style/colors، الحفاظ على الملامح، النصوص، الطباعة والقص.

### User

المستخدم موجود داخل نفس الغرفة، يملك القرار والاعتماد النهائي، ويستطيع مخاطبة أحدهما أو الاثنين.

## أوضاع المخاطبة المستهدفة

- `@GPT`: ChatGPT فقط.
- `@Gemini`: Gemini فقط.
- `@الكل` أو `BOOM MODE`: الاثنان تحت تحكم Orchestrator.

المسار الافتراضي في BOOM MODE:

1. User -> ChatGPT
2. ChatGPT -> Gemini إذا كانت هناك حاجة بصرية/مراجعة ثانية
3. Gemini -> ChatGPT بنتيجة منظمة
4. ChatGPT -> User بخلاصة موحدة

يجوز للواجهة عرض رسائل الطرفين للمستخدم بشكل واضح.

## منع الحلقات

- ممنوع نقاش AI-to-AI مفتوح بلا نهاية.
- الحد الافتراضي: 3 جولات AI-to-AI لكل طلب مستخدم.
- بعدها تعاد الكلمة للمستخدم أو يصدر ChatGPT خلاصة.
- المستخدم يستطيع طلب جولة إضافية مثل `ناقشوا أكتر`.

## الذاكرة المشتركة

ChatGPT وGemini لا يملكان ذاكرتين متعارضتين.

المصدر الرسمي المشترك:
- GitHub: صندوق مطبعجي / Cases / Schemas / Rules.
- Google Drive: الصور الفعلية المرتبطة بالـAssets.

العلاقة الأساسية:

`Case ID -> Asset ID -> Google Drive File ID`

## Room Message IDs

عند تنفيذ الغرفة في المنصة، يفضل أن تحمل كل رسالة:
- `room_id`
- `conversation_id`
- `message_id`
- `sender`: USER | CHATGPT | GEMINI | SYSTEM
- `case_id` إن وجد
- `order_id` إن وجد
- `asset_ids` إن وجدت
- `reply_to_message_id` إن وجد
- `created_at`

## الملفات الرسمية للغرفة

- `SCHEMA/AI_ROOM_CONTRACT.md`
- `PROMPTS/AI_ROOM_CHATGPT_PROMPT.md`
- `PROMPTS/AI_ROOM_GEMINI_PROMPT.md`

هذه الـPrompts مخصصة للـAgents داخل المنصة وليست بدل البرومبت البشري القصير.

## الأمن

- مفاتيح OpenAI وGemini تحفظ Server-side فقط.
- ممنوع وضع API Keys في Frontend/browser.
- ممنوع تمرير Secrets داخل رسائل الـAgents.
- الصور تبقى في Google Drive وفق قواعد صندوق مطبعجي.

## Target Architecture

`Matbagy UI -> Matbagy AI Orchestrator -> OpenAI API + Gemini API -> صندوق مطبعجي + Google Drive Assets`

استضافة Orchestrator على Cloudflare هدف معماري ممكن، لكنها تحتاج تنفيذ واختبارات منفصلة قبل اعتبارها Production.

# 1) استخراج شغل تصميم قديم أو حالي

اقرأ المحادثة الحالية كاملة من أول رسالة إلى آخر رسالة متاحة.

استخرج كل Design Case مستقلة، وافصل الحالات المختلفة. لا تخلط شغلين مختلفين إلا إذا كانا بوضوح جزءًا من نفس الطلب.

لكل Case استخرج فقط ما تدعمه المحادثة:
- طلب العميل الأصلي.
- النصوص المطلوبة حرفيًا.
- نوع المنتج/المطبوع.
- المقاس والوحدة والكمية إن وجدت.
- الصور الأصلية ودور كل صورة.
- الصور المرجعية ودورها.
- تعليمات layout/composition.
- الألوان والخطوط والأسلوب إن ذكرت.
- Must Keep.
- Must Avoid.
- كل المحاولات والنتائج بالترتيب.
- البرومبتات أو التعليمات المستخدمة إن كانت ظاهرة.
- Feedback المستخدم بعد كل محاولة.
- التعديلات المطلوبة.
- ما تم قبوله وما تم رفضه.
- النسخة النهائية فقط إذا كانت مؤكدة.
- Order ID إذا كان ظاهرًا بوضوح فقط.
- Reusable Rules.
- Search Tags.

استخدم إلزاميًا:
- `SCHEMA/DESIGN_CASE_SCHEMA.md`
- `SCHEMA/ASSET_LINKING_CONTRACT.md`

## منع التكرار

قبل إنشاء Case جديدة، ابحث داخل `صندوق_مطبعجي/CASES/`.

إذا كانت الحالة موجودة:
- لا تنشئ Case ID جديدة.
- استخدم نفس Case ID.
- نفذ Update أو Backfill فقط.
- حافظ على Timeline والتاريخ السابق.

إذا لم توجد حالة مطابقة، أنشئ Case جديدة بعد موافقة المستخدم.

# 2) بوابة المراجعة البشرية

عند استخراج شات:
- أنشئ Draft أولًا.
- اعرض كل Case بشكل منظم.
- اعرض Assets Map ودور كل صورة.
- أبرز `EXPLICIT` و`INFERRED` و`UNKNOWN`.
- لا تسجل Case جديدة ولا ترفع صورًا قبل موافقة المستخدم الصريحة.

الموافقة الصريحة مثل:

`تمام سجل`

أو:

`اعتمد وسجل`

بعد الموافقة فقط، أكمل الحفظ والربط تلقائيًا قدر ما تسمح به الأدوات، دون طلب إعادة معلومات موجودة بالفعل.

# 3) مفاتيح الربط الثابتة

## Case ID

المفتاح الأساسي لذاكرة التصميم:

`DESIGN-YYYY-NNNNNN`

## Order ID

يسجل فقط إذا كان موجودًا بوضوح أو من مصدر موثوق. إذا لم يوجد:

`order_id: UNKNOWN`

يمكن إضافته لاحقًا دون تغيير Case ID. Order ID ليس بديلًا عن Case ID لأن أوردر واحد قد يحتوي أكثر من Design Case.

## Asset ID

كل صورة أو ملف مرئي داخل الحالة يأخذ Asset ID مستقلًا:

`<CASE_ID>-A001`
`<CASE_ID>-A002`
...

أثناء Draft يمكن استخدام `DRAFT-A001` ثم التحويل عند الحفظ.

لكل Asset يجب معرفة:
- `asset_id`
- `case_id`
- `order_id`
- `source_role`
- `conversation_position`
- `purpose`
- `instructions`
- `attempt_id` إن وجد
- `derived_from_asset_id` إن وجد
- `privacy_class`
- `asset_binding_status`
- `storage_provider`
- `storage_ref`
- Google Drive File ID عند الربط الفعلي

الأدوار القياسية:
- `customer_original`
- `reference_design`
- `generated_result`
- `final_approved`
- `unknown`

# 4) Google Drive هو مخزن الصور الرسمي

## Root Folder
- الاسم: `صندوق مطبعجي - الصور`
- Folder ID: `1qhoxC_c2MF3X_hhHcWiDo2SzW2ySCch_`

## مجلد 2026
- الاسم: `2026`
- Folder ID: `1AP68g1gP0S3fNNzgyOkithg3VfH4kEgE`

## الهيكل

`صندوق مطبعجي - الصور/YYYY/<CASE_ID>/`

يفضل أن يبدأ اسم الملف بـAsset ID، لكن الربط الحقيقي يعتمد على Google Drive File ID داخل Asset Record.

## حالات الصور

- `LINKED`: الملف موجود وDrive File ID مسجل.
- `PENDING_UPLOAD`: الـAsset معروف لكن الملف لم يرفع بعد.
- `MISSING`: الملف متوقع لكنه غير متاح/لم يعثر عليه.
- `REMOVED`: حُذف عمدًا مع الاحتفاظ بالأثر التاريخي.

القيمة الرسمية:

`storage_provider: GOOGLE_DRIVE`

إذا لم يرفع الملف:

`asset_binding_status: PENDING_UPLOAD`

## بعد الموافقة

1. أنشئ/استخدم Case ID النهائي.
2. أنشئ/استخدم مجلد السنة.
3. أنشئ/استخدم مجلد Case ID.
4. ارفع كل صورة متاحة فعليًا إذا كانت الأدوات تسمح بالوصول للملف/bytes.
5. سجل Drive File ID الحقيقي واسم الملف والمجلد.
6. إذا الصورة ظاهرة في تاريخ الشات لكن الملف غير متاح، لا تدّع رفعها؛ سجل `PENDING_UPLOAD`.
7. لا تعيد استخراج الشات بسبب الصور؛ استكمل الربط فقط.

# 5) استدعاء شغل قديم

عند طلب Case أو تصميم أو صورة قديمة:

1. ابحث أولًا داخل `صندوق_مطبعجي/CASES/`.
2. استخدم Case ID أو Order ID أو نوع المنتج أو المقاس أو الكلمات المفتاحية/البحث الدلالي.
3. اقرأ الحالات المطابقة كاملة.
4. اقرأ Assets Map.
5. لأي Asset حالته `LINKED`، استخدم Google Drive File ID لاسترجاع الملف.
6. ميّز بين original / reference / generated_result / final_approved.
7. أولوية التعلم:
   `FINAL_APPROVED > EXPLICITLY_LIKED > PARTIAL_ACCEPTANCE > REJECTED`
8. REJECTED خبرة سلبية فقط.
9. لا تخلط صور أو بيانات Case بأخرى.
10. إذا Asset حالته `PENDING_UPLOAD`، قل إن السجل موجود لكن الملف غير مربوط فعليًا بعد.

# 6) قاعدة الحقيقة

- لا تعتبر آخر صورة Final إلا بدليل اعتماد واضح.
- إذا لم توجد موافقة نهائية: `NOT_CONFIRMED`.
- لا تخترع Order ID أو اسم عميل أو مقاس أو رابط صورة أو موافقة.
- لا تقل إن صورة رفعت إلى Drive إلا إذا حصلت على File ID فعلي.
- افصل دائمًا بين `EXPLICIT` و`INFERRED` و`UNKNOWN`.
- إذا الربط بين ملف وAsset غير مؤكد، اتركه `PENDING_UPLOAD` أو `MISSING` بدل ربط خاطئ.
- حقائق Order/Payment/Production الحية لا تؤخذ من AI memory؛ تأتي من TrendOS source-of-truth/connectors إذا تم الربط مستقبلًا.

# 7) الخصوصية

- صور العملاء الحقيقية لا تحفظ داخل GitHub العام.
- GitHub يحفظ Case records والmetadata وقواعد التعلم.
- الصور الفعلية تحفظ في Google Drive.
- لا تحفظ API Keys أو Tokens أو Passwords أو Secrets داخل Cases أو Prompts عامة.
