# صندوق مطبعجي

> **المدخل الرسمي لذاكرة التصميمات الخاصة بمطبعجي.**
>
> هذا الصندوق مستقل تمامًا عن **الصندوق الأسود لترند مول / TrendOS**. الصندوق الأسود خاص بذاكرة المشاريع والتنفيذ، أما **صندوق مطبعجي** فهو خاص بخبرة التصميمات: طلبات العملاء، الصور المرجعية، المحاولات، التعديلات، الرفض، القبول، والنتائج النهائية.

## قاعدة التشغيل

عندما يطلب المستخدم في أي محادثة:

- `ادخل GitHub واقرأ صندوق مطبعجي`
- أو `استخرج الشات لصندوق مطبعجي`
- أو `اقفل حالة التصميم`
- أو أي صياغة تؤدي نفس المعنى

يجب تنفيذ الترتيب التالي:

1. اقرأ هذا الملف كاملًا.
2. إذا كانت المحادثة قديمة أو المطلوب استخراجها، اقرأ `INSTRUCTIONS/EXTRACT_OLD_CHAT.md`.
3. استخدم `SCHEMA/DESIGN_CASE_SCHEMA.md` لبناء الحالة بنفس الحقول الثابتة.
4. اقرأ `SCHEMA/ASSET_LINKING_CONTRACT.md` لتطبيق Case ID / Order ID / Asset ID وقواعد ربط الصور مستقبلًا.
5. **لا تسجل أي Case في GitHub قبل عرض Draft كامل على المستخدم وموافقته الصريحة.**
6. بعد أن يقول المستخدم بوضوح مثل `تمام سجل` أو `اعتمد وسجل`، اقرأ `INSTRUCTIONS/SAVE_APPROVED_CASE.md` ثم نفذ التسجيل.
7. عند البحث لاحقًا عن خبرة سابقة، اقرأ `INSTRUCTIONS/SEARCH_MEMORY.md`.

## الهدف

تحويل كل محادثة تصميم إلى خبرة قابلة للبحث بحيث يستطيع Matbagy Smart Designer لاحقًا فهم:

`طلب العميل -> الصور/المراجع -> المحاولات -> التعديلات -> الرفض/القبول -> النتيجة النهائية -> القواعد المتعلمة`

## مفاتيح الربط من الآن

يجب تجهيز كل Case من البداية للربط المستقبلي مع الصور:

- `case_id`: المفتاح الأساسي لذاكرة حالة التصميم.
- `order_id`: يسجل فقط إذا كان ظاهرًا بوضوح؛ وإلا `UNKNOWN` ويمكن إضافته لاحقًا.
- `asset_id`: معرف مستقل لكل صورة/ملف في الحالة.

بعد حفظ الحالة يفضل أن يكون Asset ID بالشكل:

`DESIGN-YYYY-NNNNNN-A001`

أثناء الـDraft يمكن استخدام `DRAFT-A001` ثم تحويله عند الحفظ.

**Order ID لا يحل محل Case ID.** قد يحتوي الأوردر الواحد على أكثر من Design Case.

## قاعدة عدم اختراع الحقيقة

- لا تعتبر آخر صورة في المحادثة Final إلا إذا كان هناك دليل واضح على اعتمادها أو قبولها.
- إذا لم توجد موافقة نهائية، سجّل الحالة كـ `NOT_CONFIRMED`.
- لا تستنتج اسم عميل أو رقم أوردر أو مقاس أو نص غير موجود بوضوح.
- افصل بين ما طلبه المستخدم فعلًا وبين استنتاجات الـAI.

## قاعدة الصور

لكل صورة أو ملف مرئي ظاهر في المحادثة، أنشئ Asset Record يوضح دوره مثل:

- `customer_original`
- `reference_design`
- `generated_result`
- `final_approved`
- `unknown`

إذا لم يكن هناك رابط دائم أو ملف يمكن الرجوع إليه، لا تخترع رابطًا. استخدم وصفًا ومرجع ترتيب داخل المحادثة فقط، وسجّل:

- `asset_binding_status: PENDING_STORAGE`
- `storage_provider: PENDING`
- `storage_ref: PENDING`

هذا الحجز هو الذي سيمكننا لاحقًا من ربط الصورة الحقيقية بنفس الـAsset ID بدون إعادة استخراج الشات.

## مرحلة الصور لاحقًا

عند اعتماد مكان خاص للصور:

1. لا نعيد قراءة الشاتات القديمة من الصفر.
2. نفتح الـCase المحفوظة.
3. نستخدم `case_id` و`asset_id` لمطابقة الملفات.
4. نضيف مكان الصورة الحقيقي داخل Asset Record.
5. يبقى `order_id` رابطًا للبحث وربط الأوردر عند توفره.

القواعد الكاملة موجودة في:

`SCHEMA/ASSET_LINKING_CONTRACT.md`

## الأمان والخصوصية

Repository الحالي للمصمم قد يكون عامًا، لذلك:

- **ممنوع حفظ صور عملاء حقيقية أو بيانات شخصية حساسة داخل GitHub العام.**
- في المرحلة الحالية يسجل الصندوق النصوص المنظمة والـmetadata فقط، مع Asset placeholders عند الحاجة.
- أي تخزين فعلي لصور العملاء يجب أن ينتقل إلى مخزن خاص/مؤمّن قبل تفعيله إنتاجيًا.
- ممنوع حفظ API keys أو passwords أو tokens أو secrets.

## أولوية التعلم

الأولوية عند بناء ذاكرة المصمم:

`FINAL_APPROVED > EXPLICITLY_LIKED > PARTIAL_ACCEPTANCE > REJECTED`

النسخ المرفوضة لا تُحذف؛ تُحفظ كخبرة سلبية حتى يعرف المصمم الذكي ما الذي يجب تجنبه.
