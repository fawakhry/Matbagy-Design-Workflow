# Approval Command Router — صندوق مطبعجي

> الهدف: منع خلط اعتماد حفظ ذاكرة الـCase مع اعتماد التصميم النهائي أو أوامر تنفيذ/توليد الصور.

## الحالة

`ACTIVE / REQUIRED`

هذا العقد له الأولوية عند تفسير أوامر الاعتماد داخل صندوق مطبعجي.

## 1) ثلاث نوايا مختلفة يجب فصلها

### A) اعتماد حفظ الـCase / الذاكرة

الأوامر مثل:

- `اعتمد وسجل`
- `تمام سجل`
- `سجل الحالة`

تعني:

`MEMORY_PERSISTENCE_APPROVAL`

أي:
- اعتماد الـDraft المستخرج كذاكرة Case.
- تخصيص/استخدام Case ID.
- حفظ البيانات والـTimeline والـAssets Map.
- رفع/ربط الـAssets المتاحة فعليًا حسب عقد Google Drive.
- تسجيل المحاولات الفاشلة أو الناقصة كما حدثت.

**هذه الأوامر لا تعني إطلاقًا اعتماد التصميم النهائي.**

**هذه الأوامر لا تشغّل Image Generation أو Image Editing أو إعادة المحاولة.**

إذا كانت آخر محاولة صورة قد فشلت، يتم حفظها كـ:

`FAILED_NO_RESULT`

ولا يعاد تشغيل التوليد إلا بأمر تنفيذ جديد وصريح من المستخدم.

---

### B) اعتماد التصميم النهائي

الأوامر التي تدل بوضوح على أن النتيجة المرئية نفسها نهائية، مثل:

- `اعتمد التصميم النهائي`
- `التصميم ده نهائي`
- `تمام ده النهائي`
- `اعتمد النسخة دي للطباعة`

تعني:

`DESIGN_FINAL_APPROVAL`

ولا يجوز تطبيقها إلا إذا:
- توجد نتيجة/Asset فعلية قابلة للمراجعة.
- Version ID معروف أو قابل للربط بوضوح.
- يوجد Evidence واضح أن المستخدم يقصد التصميم نفسه وليس مجرد حفظ الذاكرة.

عندها فقط يمكن تحديث:
- `approval_status: FINAL_APPROVED`
- `final_version_id`
- `final_asset_id`

حسب Evidence الفعلي.

اعتماد التصميم النهائي نفسه **لا يشغّل توليد صورة جديدة**.

---

### C) أمر تنفيذ/توليد/تعديل التصميم

الأوامر مثل:

- `استخرج`
- `نفذ`
- `اعمل التصميم`
- `عدل الصورة`
- `جرب تاني`

قد تعني تنفيذ صورة/تصميم حسب سياق المحادثة.

هذه الفئة منفصلة تمامًا عن أوامر التسجيل والاعتماد.

إذا فشل التنفيذ، لا تحول أمر تسجيل لاحق إلى إعادة تنفيذ تلقائية.

---

## 2) قاعدة الأولوية عند الغموض

إذا قال المستخدم `اعتمد وسجل` بعد Draft استخراج Case، فالمعنى الافتراضي الوحيد هو:

`SAVE THE CASE MEMORY`

حتى لو كانت الرسالة السابقة محاولة توليد صورة فاشلة.

لا يجوز تفسير `اعتمد وسجل` كـ:
- Generate image
- Retry generation
- Final design approval

إلا إذا أضاف المستخدم نصًا صريحًا آخر يطلب ذلك.

## 3) فصل حالتي الاعتماد في الـCase

يفضل استخدام حقلين منفصلين:

- `memory_persistence_approval: APPROVED | PENDING`
- `design_final_approval: FINAL_APPROVED | NOT_CONFIRMED`

إذا النظام القديم يستخدم `approval_status` فقط، فلا تحوله إلى `FINAL_APPROVED` بسبب `اعتمد وسجل` وحدها.

في هذه الحالة:
- الـCase يمكن أن تكون `SAVED`.
- بينما `approval_status` للتصميم يظل `NOT_CONFIRMED`.

## 4) بعد فشل Image Generation

إذا أرجعت أداة الصور Failure أو لم تنتج Result قابل للمراجعة:

1. سجل Version/Attempt كـ`FAILED_NO_RESULT`.
2. لا تنشئ `result_asset_id` وهمي.
3. لا تعتبر التصميم Final.
4. إذا قال المستخدم بعدها `اعتمد وسجل`، احفظ الـCase كما هي مع Evidence الفشل.
5. لا تعاود تشغيل الصورة إلا بأمر صريح مثل `جرب تاني` أو `نفذ التصميم`.

## 5) Safe to delete

حفظ الـCase بعد `اعتمد وسجل` يمكن أن يجعل الشات آمنًا للحذف فقط إذا تم التحقق فعليًا من:
- حفظ Case record.
- حفظ/ربط كل Source Assets المتاحة أو وسم غير المتاح بوضوح.
- حفظ Timeline والمحاولات والفشل.

وجود تصميم Final ليس شرطًا لحفظ Case تاريخية إذا لم توجد نتيجة Final أصلًا.

لكن يجب أن يبقى:

`design_final_approval: NOT_CONFIRMED`

ولا يجوز اختراع Final Asset.

## 6) عبارات تأكيد النظام

بعد نجاح حفظ الـCase:

`CASE_PERSISTED`

وعند تحقق شروط حذف الشات كلها:

`SAFE_TO_DELETE_CHAT`

أما إذا لم يتم الحفظ فعليًا:

`NOT_SAFE_TO_DELETE_CHAT — PERSISTENCE_NOT_CONFIRMED`

## 7) قاعدة نهائية

`PERSISTENCE APPROVAL != DESIGN FINAL APPROVAL != EXECUTION COMMAND`

الثلاثة نوايا مستقلة ويجب عدم دمجها في أي Agent أو Chat أو Orchestrator.
