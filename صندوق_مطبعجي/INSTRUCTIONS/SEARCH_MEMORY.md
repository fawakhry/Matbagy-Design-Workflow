# البحث والاستدعاء في ذاكرة صندوق مطبعجي

## الهدف

استخدم الحالات القديمة كخبرة قابلة للاستدعاء، مع الحفاظ على أولوية طلب العميل الحالي وعدم اختراع أي حقيقة.

## ترتيب البحث

1. Case ID إذا أعطاه المستخدم.
2. Order ID إذا كان المستخدم يكمل نفس الأوردر.
3. نفس العميل إن كانت هويته مؤكدة.
4. نفس نوع المنتج.
5. نفس المقاس أو التكوين.
6. نفس الكلمات المفتاحية/الستايل.
7. FINAL_APPROVED أولًا، ثم EXPLICITLY_LIKED، ثم PARTIAL_ACCEPTANCE.
8. REJECTED يستخدم فقط كخبرة سلبية.

## استرجاع الصور

بعد العثور على Case مناسبة:

1. اقرأ `case_id`.
2. اقرأ Assets Map.
3. لكل Asset اقرأ `asset_id`, `source_role`, `attempt_id`, `asset_binding_status`.
4. إذا كانت `LINKED`، استخدم `drive_file_id` أو `storage_ref` للوصول إلى الملف من Google Drive.
5. إذا كانت `PENDING_UPLOAD`، قل بوضوح إن سجل الصورة موجود لكن الملف نفسه لم يُرفع بعد.
6. إذا كانت `MISSING` أو `REMOVED`، لا تدّعِ أن الصورة متاحة.
7. ميّز بين customer_original وreference_design وgenerated_result وfinal_approved قبل الاستخدام.

## ما الذي يستفاد من النتائج؟

- التكوينات التي نجحت.
- قواعد النص والمقاس.
- الألوان والخطوط.
- الرفض المتكرر.
- تعليمات المحافظة على الصور والملامح.
- الصور والمراجع المرتبطة فعليًا.
- Reusable Rules.

## ممنوع

- لا تخلط Case بأخرى.
- لا تنقل صورة عميل إلى عميل آخر بلا سبب وصلاحية واضحة.
- لا تستخدم تصميمًا مرفوضًا كمثال إيجابي.
- لا تخترع Drive File ID أو رابطًا.
- لا تعتبر صندوق مطبعجي مصدرًا لحقائق الدفع أو الإنتاج الحية.

## المخرج عند الاستدعاء

إذا طلب المستخدم استدعاء حالة محددة، اعرض باختصار:

- Case ID
- Order ID إن وجد
- ملخص الطلب
- Approval status
- Assets وحالتها
- الصورة/الملف المرتبط إن كان LINKED
- Reusable Rules ذات الصلة

إذا طلب شغلًا مشابهًا، رتّب النتائج بحسب التشابه ثم قوة الاعتماد.
