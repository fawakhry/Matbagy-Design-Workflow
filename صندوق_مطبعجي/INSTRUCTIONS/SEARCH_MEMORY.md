# البحث في ذاكرة صندوق مطبعجي

## الهدف

عند وصول طلب تصميم جديد، استخدم الحالات القديمة كخبرة مساعدة لا كمصدر حقيقة نهائية.

## ترتيب البحث

1. نفس `order_id` إذا كان المستخدم يكمل نفس الأوردر.
2. نفس العميل إن كانت هويته مؤكدة.
3. نفس نوع المنتج.
4. نفس المقاس أو التكوين.
5. نفس الكلمات المفتاحية/الستايل.
6. حالات FINAL_APPROVED أولًا.
7. حالات EXPLICITLY_LIKED ثم PARTIAL_ACCEPTANCE.
8. استخدم REJECTED فقط كأمثلة سلبية لما يجب تجنبه.

## استرجاع الصور المرتبطة

بعد العثور على Case مناسبة:

1. اقرأ `case_id`.
2. اقرأ Assets map الخاص بها.
3. لكل Asset اقرأ `asset_id` و`source_role` و`attempt_id`.
4. إذا كانت `asset_binding_status = LINKED`، استخدم `storage_ref` عبر طبقة التخزين المصرح بها.
5. إذا كانت `PENDING_STORAGE` أو `MISSING`، لا تدّعِ أن الصورة متاحة؛ استخدم الـMetadata فقط.
6. عند التعلم أعط أولوية لصورة `final_approved`، واستخدم الصور المرفوضة كـnegative examples فقط.

بهذا يعرف الـAI أن الصورة تخص الشات/الحالة من `case_id + asset_id`، وليس من اسم الملف فقط.

راجع `../SCHEMA/ASSET_LINKING_CONTRACT.md` لأي تفاصيل ربط.

## ما الذي تستخرجه من النتائج؟

- أنماط التكوين التي نجحت.
- قواعد النصوص والمقاسات.
- تفضيلات الألوان والخطوط.
- الأشياء التي تكرر رفضها.
- تعليمات المحافظة على الصور/الملامح.
- الصور/المراجع المرتبطة إذا كانت متاحة بشكل آمن.
- عدد التعديلات المعتاد إن كان له معنى.
- أمثلة مشابهة قابلة لإعادة الاستخدام.

## ممنوع

- لا تفترض أن عميلًا جديدًا له نفس ذوق عميل سابق.
- لا تنقل بيانات شخصية من عميل إلى آخر.
- لا تستخدم تصميمًا مرفوضًا كمثال إيجابي.
- لا تعتبر ذاكرة الصندوق بديلًا عن طلب العميل الحالي.
- لا تعتبر الـAI مصدرًا لحقائق Order/Payment/Production الحية.
- لا تخترع `storage_ref` أو رابط صورة غير موجود.

## المخرج المفضل للمصمم الذكي

قبل التنفيذ، كوّن داخليًا Design Context مختصرًا:

- Current Request
- Current Order ID if explicit
- Similar Approved Cases
- Relevant Linked Assets
- Relevant Reusable Rules
- Negative Patterns To Avoid
- Confidence

ثم نفذ الطلب الحالي مع إعطاء طلب العميل الحالي الأولوية الأعلى.
